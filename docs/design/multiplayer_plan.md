## 목표 / 제약
- **엔진 재작성 없음**: 엔진은 이미 JSON 직렬화·스냅샷·공유 코드(BTB1)·moveLog 가 있어 netcode 친화적.
  온라인은 "스냅샷/수를 두 브라우저 사이로 중계"하는 얇은 층만 얹으면 된다.
- **현재 배포는 정적(GitHub Pages)** — 서버가 없다. 온라인 대전엔 **최소한의 백엔드(중계)** 가 꼭 필요하다
  (두 브라우저가 서로 직접 못 본다). 순수 정적만으로는 불가능.
- **초보 친화 + 무료**: 계정·서버 운영 부담을 최소화. 무료 티어 안에서.
- **로컬 핫시트 / vs AI 는 그대로 유지** — 온라인은 새 모드로 추가(기존 흐름 안 깨기).

## 핵심 결정 (사용자 확인 필요)

### 1) 동기 모델 — 비동기 턴제 vs 실시간
- **(A) 비동기 턴제(추천)**: 둘이 동시에 접속 안 해도 됨. 내가 두면 방 상태가 갱신되고, 상대가 다음에
  열면 이어서 둔다(상대가 접속 중이면 실시간으로 바로 보임). 턴제 추상 전략에 자연스럽고 인프라가 가볍다.
- **(B) 실시간 전용**: 둘 다 접속해 있어야 진행. 접속 표시·재접속·이탈 처리 등 신경 쓸 게 많다.
- → **추천 A**. 백엔드의 실시간 구독을 쓰면 "동시 접속이면 실시간, 아니면 비동기"가 공짜로 따라온다.

### 2) 백엔드 — 무엇으로 중계할까
- **(A) Supabase(추천)**: Postgres + Realtime(행 변경 구독) + 익명 인증. 무료 티어 넉넉, 문서 친절.
  방 = 한 행(스냅샷 + moveLog + 차례). 클라이언트는 anon key 로 그 행을 구독·갱신.
- **(B) Firebase**: Firestore/Realtime DB 로 동일 구현. 구글 계정 기반.
- **(C) WebRTC P2P(PeerJS)**: DB 없이 브라우저끼리 직접. 단 **둘 다 동시 접속 필수(비동기 불가)** +
  시그널링 서버 필요(공용은 불안정). 턴제·비동기엔 부적합.
- → **추천 A(Supabase)**: 비동기+실시간 한 번에, 무료, 익명방 가능. 셋업 = 무료 프로젝트 1개 + anon key
  를 클라이언트 env 에 넣기(공개돼도 되는 키, RLS 로 방 단위 접근 제한).

### 3) 인증 / 방 모델
- **계정 없음(추천)**: 방 코드(또는 초대 URL `#room=<id>`)만으로 참가. 익명 세션 id 로 두 플레이어 구분.
  나중에 닉네임 정도만 선택. (CLAUDE.md "초대링크 방"과 일치.)

## 추천 아키텍처 (결정 시)
- **방(room)** = 백엔드의 한 레코드: `id`, `snapshot`(BTB1 문자열), `move_log`, `turn`, `players`(2),
  `status`(waiting/playing/finished), `updated_at`.
- **흐름**: 방장 "방 만들기" → room 생성 + 초대 URL 복사 → 상대가 URL 로 입장(빈 슬롯 차지) →
  각자 자기 차례에 로컬에서 수 두고 새 스냅샷 push → 상대 클라이언트가 구독으로 받아 applySnapshot.
- **엔진 재사용**: 수 적용·합법성·승패는 **기존 엔진 그대로**(로컬과 동일). 네트워크는 스냅샷 전달만.
  치팅 방지는 1차 범위 밖(친구끼리 대전 전제). 추후 서버측 검증 옵션.
- **UI**: 모드에 "온라인" 추가. 내 차례가 아니면 입력 잠금 + "상대 차례" HUD. 연결 상태 표시.

## 단계 (방향 확정 후)
1. **Phase 1 — 방 + 수 동기화(MVP)**: 방 만들기/입장(초대 URL), 스냅샷 push/subscribe 로 양쪽 동기화,
   내 차례만 입력. 둘이 한 판 끝까지.
2. **Phase 2 — 견고화**: 재접속/새로고침 복원, 상대 이탈·연결 끊김 표시, 동시 수 충돌 방지(turn 가드).
3. **Phase 3 — 편의**: 닉네임, 재대국, 관전 링크, 로비 목록(선택).
